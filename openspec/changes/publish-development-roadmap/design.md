# Design

## Context

当前行为见主规格与 `docs/status.md`。已有 Chat、用户归属、附件、配置发布快照和证据记录；后续路线图应在这些能力上补齐验收与增量功能，不能将历史设计的完整目标当成已交付事实。动机见 `proposal.md`。

## Goals / Non-Goals

**Goals:** 每项实施工作都有独立交付物、前置条件与可观察的退出条件；总路线图与正式设计互相链接。发布范围严格为一个总 Issue、十三个实施 Issue 及文档。

**Non-Goals:** 本次不实现十三项功能，不调整当前应用规格，不更改原运行实例，不新增图片、部署、版本标签或 Release。

## Decisions

1. 使用稳定规划编号 R01–R13，另记录 GitHub 实际编号。R 编号表示设计中的工作包；GitHub 编号用于跳转，避免预猜编号或后续改号引起歧义。
2. 四阶段按成果组织：M1 分析准确性、M2 工作台完善、M3 场景扩展、M4 自动触发。保留原 P0–P4 设计阶段，新增映射；不将这些阶段转换为未确认的版本号或日期承诺。
3. 区分硬依赖与集成依赖。R05 管理验收与 R07 数据源权限可并行，其交叉场景在两者集成时验收；R12 核心根因流程不以工单接入为前置，工单维度接入后另验。R13 以分析报告、配置快照、授权和恢复契约齐备为启动门槛。
4. Issue 包含目标、已有基础、交付范围、非目标、依赖、验收清单及建议 OpenSpec 变更名。发布时全部保持 open、验收项未勾选。代码、检查、业务验收、用户接受分别记录，不能以 Issue 创建代替功能完成。
5. 发布前使用现有扫描器的完整规则与仓库外私有 profile 校验准确的 Issue 标题/正文快照；只读获取私有比对值，临时扫描树隔离于原运行实例。生成文档后再检查实际暂存树和提交历史。扫描失败时先修复草稿，不降低规则。
6. 先查重，再创建总 Issue 与十三个子工作项，依赖使用实际链接；最后更新总表并读回全部十四项核对。网络结果不明时先按稳定标题查询，不能直接重试造成重复。

## Risks / Trade-offs

- [规划与交付状态混淆] → 路线图显式标为规划；R01 建立基线不要求现有应用通过全部未来能力，阶段退出另行验收。
- [重复工作或依赖环] → 复用已有管理、Chat 和持久化模块；硬依赖图做无环检查，交叉集成单独标记。
- [Issue 与文档漂移] → 本轮从同一份结构化草稿生成正文与正式路线图，实际编号回填后逐项对比读回内容；后续范围调整同时更新 Issue 与路线图。
- [公开规划带入现场信息] → 使用通用案例，不包含真实资产、地址、端点、配置、截图或原始收据；已知私有值比对仅输出计数与结果。

## Migration Plan

本次无运行迁移。文档提交正常推送并核对对应 CI；发布结果及保留边界记入验证文档。后续实施各自建立 OpenSpec 变更，先核对本路线图依赖，再按对应验收完成。
